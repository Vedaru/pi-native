# ADR 0002: TUI — native renderer with a JS component bridge

- Status: Accepted
- Date: 2026-10-04
- Issue: VED-319 (decision), updates VED-307
- Deciders: pi-native maintainers

## Context

VED-307 assumed we port pi's TUI to Rust. Before committing, we compared that
with reusing pi's original TypeScript TUI. The TUI is not only a renderer: pi
extensions can inject **custom components** into it, so it is also a
compatibility surface.

## Measurements

| Fact | Value |
| --- | --- |
| Interactive TUI idle RSS (no session) | 117.0 MB |
| Headless RPC idle RSS | 111.7 MB |
| TUI delta over headless at idle | **+5.3 MB** |
| `packages/tui` source | 19,277 lines |
| interactive mode source | 21,626 lines |
| Example extensions | 86 |
| … using `ctx.ui` hostcalls (`notify`/`select`/`confirm`/`input`) | **59 (69%)** |
| … using the `Component` API / `render(` | 12 / 17 files (~14–20%) |
| … using `registerMessageRenderer` | 2 files |

The TUI's idle delta is small because the interactive code is already loaded in
the headless path (a static import in `main.ts`). The real costs are the live
component graph during long sessions and the engine executing the TUI every
frame.

## Decision

**Native Rust renderer with a JS component bridge.**

- The transcript, tool output, editor, and layout are rendered natively in Rust
  on the hot path.
- Extensions that register custom `Component`s keep working through a bridge:
  the component's `render()` runs in the embedded QuickJS host, and its produced
  lines are composited by the native renderer.
- `ctx.ui` (`notify`/`select`/`confirm`/`input`) are implemented as native
  dialogs behind the existing hostcalls — this is what 69% of extensions use.
- `registerMessageRenderer` and `registerMarkdownTransformer` are delivered
  through the same bridge.

## Rationale

- Reusing the TS TUI requires running it every frame. Under QuickJS that is slow
  (no JIT); under Node it keeps the V8 baseline we are removing. Neither fits.
- A pure Rust TUI breaks the ~14–20% of extensions that render custom
  components. Those are a defining feature, so they must keep working.
- The bridge confines JS to the extensions that actually need it, keeping the
  common path (69% hostcall-only, plus all core rendering) native.
- It matches the established principle: one generic mechanism (render lines from
  a component), not a special case per extension.

## Consequences

- VED-307 is scoped to: native renderer core, the `ctx.ui` hostcall dialogs, and
  the JS `Component` bridge. It is **not** descoped or cancelled.
- We must implement pi's `Component` line protocol in the bridge and keep
  `render()` calls cheap (incremental, invalidate-on-change).
- The bridge is the only place the TUI depends on the JS host; if it proves too
  costly, it can move to a worker without changing the native renderer.

## Alternatives considered

- **Pure Rust TUI (original VED-307).** Lowest memory, but breaks custom
  component extensions. Rejected.
- **Reuse the TS TUI unchanged.** Best extension compatibility, but every frame
  runs in a JS engine: slow under QuickJS, or keeps Node/V8. Rejected.
